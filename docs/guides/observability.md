# Logs and metrics

Meta's public server assigns each request a random `X-Request-ID` and writes logs to standard error. The default is compact, readable text in both development and production. The ID is generated by the server; an incoming `X-Request-ID` is not trusted or reused. Request records contain the route ID, method, status, outcome, and duration. Loader and action operation records include the same request ID.

For example, development output looks like:

```text
20:06:34  INFO  GET  200  page.templ  1.100ms  id=24d63ae32d026a32e8220a8558b39c48
20:06:41  INFO  loader execute  posts/[postId]/page.templ  ok  0.004ms  id=0ab6cdf4c68b52572782e15c2923b452
20:06:43  INFO  GET  404  /missing (unmatched)  0.066ms  id=884cf50f970aac50a0822629d1117ff4
```

Logging is enabled by default. Default logs show the requested path for unmatched requests, but omit query strings. Custom JSON logs omit arbitrary raw paths. Neither format includes cookies, request bodies, cache keys, or arbitrary Go error text. Paths can themselves contain sensitive data, so treat logs accordingly. An `error` outcome means an operation failed; it does not include the error message. Application code and third-party middleware can still log sensitive data, so review their logging separately.

`unmatched` means no registered page, API, action, or image route was identified. Browsers also make background requests, so a 404 may not correspond to the page you opened. Default logs display the path with `(unmatched)`; custom JSON logs retain the bounded `unmatched` label. Common fixed browser paths such as `/favicon.ico` are labeled in both formats.

Default status codes use colors when output goes to a terminal: green for 2xx, yellow for 4xx, and red for 5xx. Set `NO_COLOR=1` to disable color or `FORCE_COLOR=1` to enable it when piping output. Custom JSON loggers are never colored by Meta.

## Configure logging and metrics

In `cmd/app/main.go`, import `log/slog`, `os`, and `github.com/akashKarmakar02/meta/observability`. Configure the server before calling `server.New`:

```go
metrics := observability.NewCollector()
cfg.Observability = &observability.Config{
    Logger:  slog.New(slog.NewJSONHandler(os.Stderr, nil)),
    Metrics: metrics,
}
```

A nil `Observability` configuration uses the default readable logger and does not collect metrics. An explicitly configured logger takes precedence in either mode. Set `DisableLogging: true` to turn off framework request and operation logs; request IDs and any configured metrics remain enabled. `metrics.Snapshot()` returns a copy of the process-local counters and total durations in nanoseconds. The collector resets on restart; aggregate across instances in your monitoring system. Meta does not expose metrics over HTTP automatically.

A custom metrics system can implement `observability.Observer` and consume `Event` values. The callback runs synchronously and must be concurrency-safe and fast. Events contain bounded framework route identities and outcome categories, not request IDs or raw URLs. Do not add request IDs, user IDs, raw paths, or cache keys as metric labels. The built-in collector is intended for bounded route and operation sets, not arbitrary application-supplied labels.

`observability.RequestID(ctx)` retrieves the ID in a loader or action for correlation with your own safe logs. Loader and action events are recorded around their execution. A denial before execution produces a request record but not a loader or action execution event. Image requests and transformations are observed when Meta's image endpoint is mounted; an unconfigured endpoint reports its 501 response as an image request failure.

## Cache operations

Wrap an application-owned `cache.Store` to observe its `Get`, `Set`, and `Delete` calls when a request context carries observability state:

```go
store := observability.WrapCache(memoryStore)
invalidator, err := loader.NewInvalidator(store)
// Use this same store in every CacheOptions using invalidator.
```

The original owner remains responsible for closing the underlying store. Operations without an instrumented request context do not emit events. Coalesced loaders can run with a shared context that intentionally excludes request-local values, so their background fill operations may not carry the initiating request's metrics context. Image disk-cache events are observed by the image endpoint separately.

## Example application

Start the example in development mode:

```sh
meta dev
```

Open `/posts/42` to run a loader, request `/cache-demo/post/42` twice within two seconds to produce cache miss and hit events, and open `/guestbook` to submit a form action. Open `/_meta/diagnostics` for the current process's metrics JSON. The example collects metrics by default; set `GO_META_OBSERVABILITY=0` before starting it to disable collection and the diagnostics endpoint. Request logs and request IDs remain enabled. The unauthenticated diagnostics endpoint is only mounted when running behind Meta's loopback development proxy; production applications should export metrics through their own access-controlled monitoring system.

For the image endpoint, request `/_meta/image?src=%2Fimages%2Fhero.jpg&w=320&f=webp`. The ordinary example build returns 501 but still records an image request. A build with the optional native image backend can record transformations; see the image documentation in the repository README. The endpoint does not log image source paths.

Each response has a new `X-Request-ID`. Find that ID in the terminal logs to correlate request and operation records. `/_meta/diagnostics` itself is counted after its response completes, so its current request appears in a later snapshot.
